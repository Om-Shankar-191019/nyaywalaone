Architecture · technology choices · workflow

1. What the system is, in one page

Nyaywala is a web application that grades C programming assignments the same way every time, and explains every mark it gives.

Three ideas hold it together:

  1. Grading is data, not code. The marking scheme (“rule set”) is a JSON document an instructor edits in the browser. Change it and the marks change for everyone — no deploy.
  2. The same input must produce the same output. Four inputs — the source, the rule set, the test set and the toolchain — are hashed into an evaluation key. Same key, same stored evaluation; and the produced report has its own report hash anyone can re-check.
  3. Nothing is pretended. If the sandbox cannot enforce a memory limit, or an optional checker has no API key, the report says so instead of quietly scoring zero.

2. The complete workflow, drawn

2.1 One request, from click to database

Browser — a page calls fetch('/api/…'); cookies ride along automatically
▼
Express middleware, in this order
helmet (headers) → JSON body limit → cookie parser → origin check (mutations must come from our own origin) → rate limit → request-shape guard (no prototype pollution, no binary) → route
▼
Auth middleware
verify the short-lived JWT → re-read the user from the database (so a role change applies immediately) → attach req.user
▼
Authorisation, twice
1) role guard (requireRole) 2) resource guard (requireEnrolled, requireCourseOwner) — foreign ids answer 404, never 403, so ids cannot be probed
▼
Route handler — validates with Zod, then calls a service (submission, queue, grading)
▼
Prisma → PostgreSQL — typed query, transaction where it matters
▼
One envelope out — { data } on success, { error: { code, message, details? } } on failure

Why one envelope: the browser client has exactly one place to read errors, and every failure has a stable machine code (ASSIGNMENT_NOT_PUBLISHED, PROVIDER_BUDGET_EXCEEDED, …) plus a sentence a human can act on.

2.2 A submission, from upload to report

1 · Upload — student presses “Submit and grade”; the file must end in .c, be text, and be ≤ 64 KB
▼
2 · Checks before anything expensive — assignment published? not closed? under the per-student daily limit? source not binary?
▼
3 · Record the attempt — normalise line endings, store source + source_hash (sha256) + attempt number
▼
4 · Build the evaluation key = sha256(source_hash · rules_hash · testset_hash · toolchain_hash · grader_version)
▼
5 · Answer immediately — create an Evaluation row with status QUEUED, return 202 + its id. The browser starts polling.
▼
6 · Claim — the worker takes one row with SELECT … FOR UPDATE SKIP LOCKED and stamps it RUNNING
▼
7 · Gate — compile once. Compile error? stop and produce a partial report. Infinite loop suspected? skip the execution-dependent checkers.
▼
8 · Analyzers in rule order — each writes a MetricResult (score 0–1, weight, integer contribution, evidence)
▼
9 · Score — grade = clamp(round(Σ score × weight × 100), 0, 10000), then report_hash over the canonical report
▼
10 · Store & serve — evaluation SUCCEEDED/PARTIAL; the report is readable as JSON or text, gated until the instructor releases it

2.3 A whole cohort, batch-graded

Instructor presses Grade all in the cohort tab
▼
POST /api/assignments/:id/grade-all — queues one evaluation per submission that has none (owner only)
▼
Cron calls POST /api/internal/drain with X-Cron-Secret (the route is 404 while the secret is unset)
▼
drain({limit, concurrency}) — claims up to EXEC_MAX_INFLIGHT rows, runs the same pipeline as a single submission, retries up to 3 attempts
▼
Progress strip — GET /assignments/:id/grading-progress polled every 3 s gives done / total / queued / running / failed
A bug this flow exposed. The claim stamps a row RUNNING before grading, and the coordinator used to skip rows already marked RUNNING — so every claimed row was skipped and stranded forever, and batch grading silently graded nothing. Fixed: only SUCCEEDED/PARTIAL are skipped. A maintenance script (scripts/requeue-stuck.js) recovers rows stranded by the older build.

3. Feature by feature

Same twelve questions as before, now answered technically: purpose, how it is built, which technology, and why that technology. Every “where” is a real file in this repository.

3.1 Accounts, sessions and roles

AspectDetail
PurposeKnow who is asking, keep them signed in for a working session, and keep students out of instructor functions.
HowRegister hashes the password with bcrypt (cost 10). Login issues a 15-minute HS256 access JWT and a 256-bit random refresh token in httpOnly, SameSite=Lax cookies. Only the refresh token's SHA-256 is stored. Refresh rotates the token; replaying a revoked one revokes every session for that user. Every request re-reads the role from the database.
Wherebackend/src/auth/{password,jwt,cookies,sessions,middleware,rbac}.js, routes/auth.js; client side frontend/src/auth/AuthProvider.jsx, api/client.js (single-flight 401 refresh).
WhyRejected hosted auth (Clerk/Auth0): a vendor and a callback URL per environment for ~200 lines. Rejected bearer tokens in localStorage: an XSS bug would hand over the session. Cost accepted: the API must be same-origin in production, which the Vercel rewrite already gives.

3.2 Courses, join codes and enrolment

AspectDetail
PurposePut students in a class without invitations or spreadsheets, and make membership the authorisation boundary.
HowAn 8-character code, unique, compared case-insensitively; joining is idempotent (a unique (courseId, studentId) row). Enrolment rows are what requireEnrolled reads.
Whereroutes/courses.js, table enrollments.
WhyMembership as a table row (not a field on the user) means a student can be in several courses and removal is one delete. Everything else in the app can ask one cheap question: “is this person enrolled?”

3.3 Assignments and hidden test cases

AspectDetail
PurposeDefine the work and the inputs used for correctness marking.
HowAssignment: title, description, due date, allowLate, publishing state, activeRuleSetId. Test case: input, expected output, ordinal, optional hidden label. Publishing is refused unless tests exist, a rule set is published, and an oracle (reference solution) is present where a checker needs it.
Whereroutes/assignments.js, prisma/schema.prisma (Assignment, TestCase), UI pages/instructor/Assignment.jsx (Tests tab, bulk paste).
WhyTests are rows, not files, so the editor can add, edit, delete and bulk-paste them, and the same set is hashed into testset_hash — change a test and the evaluation key changes, so old reports stay explainable.

3.4 The rule-set editor (the marking scheme as data)

AspectDetail
PurposeLet an instructor change what is worth what, safely, without a deploy and without breaking past marks.
HowA rule set is validated by Zod (schema_version, limits, on_unavailable, metrics[]). Weights must sum to 1.00 (±0.001) and each analyzer's params are validated by that analyzer's own paramsSchema. Publishing freezes a new version and stores rules_hash (RFC 8785 canonical JSON). The editor builds its form from the analyzer registry, shows a live weight total, blocks publish when it is wrong, and diffs the new version against the active one.
Wheregrading/rules.js, grading/canonical.js, grading/registry.js, routes/assignments.js (publish), UI pages/instructor/RulesPanel.jsx + lib/rules.js.
WhyData, not code: a new rubric is a new row, so every past report keeps pointing at the version that produced it. Canonical hashing (RFC 8785) means key order and whitespace cannot change a hash — the same rubric always hashes the same.

3.5 Submitting source

AspectDetail
PurposeAccept a C file quickly and honestly, and start grading without making the browser wait.
HowChecks: extension .c, ≤ 64 KB, no NUL byte, not binary (control-character ratio), assignment published, not late (unless allowed), under the per-student daily ceiling. Source is normalised (CRLF→LF) and hashed; attempt numbers are allocated with a unique constraint and retried on collision. Response is 202 + evaluation id; the UI polls with backoff and shows the current stage.
Whereservices/submission-service.js, routes/submissions.js, lib/guards.js; UI pages/student/Assignment.jsx, lib/validation.js.
Why202 + polling instead of a long request: grading talks to a remote sandbox for seconds, and a serverless request that waits is a request that times out. The limits exist because the alternative is a queue full of 500 MB uploads.

3.6 The report a student reads

AspectDetail
PurposeTurn a number into something a student can act on, and something a teacher can defend.
HowGrade out of 100 with a verdict band (≥75 Good, ≥50 Needs work, else Review required; “Does not finish” when an infinite loop is suspected; “Not graded” when the evaluation failed). One row per metric: score, weight, integer contribution, evidence. A source-vs-reference diff where an oracle exists. A Limitations block generated from the provider's capability record and a versioned limitations file. The report_hash is copyable. Downloads: JSON and plain text, plus a print stylesheet.
Wherepages/student/Report.jsx, components/report-parts.jsx, lib/diff.js, grading/versions.js, grading/limitations.json.
WhyMarks without evidence are unarguable in both directions. Showing weight × score makes the arithmetic inspectable; showing limitations prevents “we measured nothing” from looking like “you failed”.

3.7 The cohort table, release and regrade

AspectDetail
PurposeGive the instructor one place to see, filter, export, release and re-run marks.
HowServer-side filters + pagination over submissions joined to their latest evaluation. CSV export streams a stable column set. PATCH /submissions/:id/release sets/clears releasedAt; students only see grades when it is set. POST /submissions/:id/regrade creates a new evaluation with lineageOfId pointing at the previous one.
Whereroutes/submissions.js, routes/assignments.js (export), UI Assignment.jsx CohortPanel.
WhyRelease is a column, not a state machine: a mark can be shown and hidden again while a query is disputed. Regrade never overwrites — lineage keeps the audit trail that a dispute needs.

3.8 Batch grading: the queue

AspectDetail
PurposeGrade a cohort at a rate the remote sandbox tolerates, without losing rows or double-charging.
HowclaimNextEvaluation uses SELECT … FOR UPDATE SKIP LOCKED so two workers never take the same row; a claim older than 15 minutes is reclaimable (a crashed worker cannot block the queue). Failures retry up to 3 attempts then stop. drain({limit, concurrency}) loops until empty or the limit is reached. Progress is one aggregate query.
Whereservices/queue.js, routes/submissions.js (grade-all, grading-progress), scripts/load-check.js, scripts/requeue-stuck.js.
WhyThe database is the queue. A separate broker (Redis/SQS) would be a second thing to run, monitor and pay for, while Postgres already has the row locks a queue needs. Cost accepted: throughput is bounded by the database, which is fine at class scale (measured: 3 submissions drained in 41 s at concurrency 1).

3.9 Similarity review

AspectDetail
PurposePoint an instructor at suspiciously similar work without turning a number into a punishment.
HowSource is tokenised and normalised, then MinHash-signed over 7-token shingles (128 permutations, seed 42). Every pair is compared; pairs above 0.85 are stored with their score. A match row carries an instructor decision (acknowledged / flagged) and a note; the grade is never changed by it.
Wheregrading/analyzers/similarity.js, grading/similarity-scan.js, routes/assignments.js, UI SimilarityPanel.
WhyMinHash makes an O(n²) comparison cheap enough for a class and deterministic (fixed seed, fixed shingle size). Advisory-only because plagiarism is a human judgement, and a false accusation is worse than a missed one.

3.10 Activity feed, theme, accessibility

AspectDetail
PurposeMake changes traceable, and make the app usable on a phone and with a keyboard.
HowPublishes, releases, regrades and similarity decisions write an audit row, read back as a chronological feed. Theme is system | light | dark in localStorage under nyaywala-theme, applied by an inline script in index.html before the first paint. Layout reflows to 360 px; forms use real labels; axe-core is part of the test run.
Wheregrading/* + routes (audit), frontend/index.html, theme/ThemeProvider.jsx, e2e/tests/theme-and-a11y.spec.js.
WhyThe inline script is the only reliable way to avoid a white flash: React renders too late, so the class must be on <html> before the stylesheet paints.

4. Inside the grading engine: the ten analyzers

Each analyzer answers one question and returns a score between 0 and 1 plus the evidence behind it. The default rule set weights them like this:

AnalyzerWeightThe question it answersHow it answers itSandbox calls
io_tests (correctness)0.20Does the program produce the right output?Runs every assignment test; compares output after trimming trailing whitespace and CRLF; score = passed ÷ total (partial credit on by default).1 per test
compiler_warnings (syntax)0.10Does it compile cleanly?Counts compiler diagnostics from the single compile gate; max(0, 1 − warnings × 0.1).0 (reuses compile)
static_analysis (structure)0.10Is it structured sanely?tree-sitter AST: mean of decayed cyclomatic complexity, function length and nesting depth against limits.0
function_split (modularity)0.10Is it broken into functions?Counts functions, rewards a helper, penalises a long main: 0.4 count + 0.2 helper + 0.4 main.0
edge_case_runner (logical)0.10Does it survive inputs the tests forget?Generates zero / negative / overflow / whitespace cases, runs the student's program and — when a reference exists — the oracle, then compares. Without an oracle the score is capped at 0.5.1 per case + 1 per oracle input (cached)
complexity_estimator0.10Is it as fast as required?Infers an order class (O(1) … O(2^n)) from loop bounds and recursion in the AST; each level over the required class costs 0.25.0
memory_audit0.10Is memory handled safely?Pattern checks for leaks, unchecked allocation, banned calls (gets, strcpy, sprintf); optional AddressSanitizer run.0, or 1 with ASan
style_analysis0.10Is it readable?Identifier length, comment ratio and line length, blended and clamped; deliberately cosmetic.0
similarity_flag0.10Is it original?MinHash over 7-token shingles vs every other submission; 1 below 0.5 similarity, decaying to 0 at 1.0.0
llm_review0.00Can a model add useful prose?Groq Llama 3.3 70B, temperature 0, fixed seed, cached by prompt hash; advisory text only.1 HTTP (not sandbox)
Why the LLM has weight 0. A model call is the least reproducible thing in the system: the provider can change the model without telling us, and then two identical submissions would earn different marks. Prose is useful; a mark that cannot be defended is not.

How an analyzer is added

  1. Create grading/analyzers/<name>.js exporting { name, supports, paramsSchema, run }.
  2. Register it in grading/registry.js — the rules editor builds its form from paramsSchema, so the UI needs no change.
  3. Add its version to ANALYZER_VERSIONS in grading/versions.js. That changes toolchain_hash, so old reports stay explainable.
  4. Add a unit test with a fixed source and an asserted score.
  5. Document it in docs/rules-reference.md.

This is the extensibility claim in practice: a new check is a file plus a registry line, not a migration of the scoring code.

5. How a mark is computed, exactly

A metric returns score in 0–1. The coordinator turns each into an integer contribution in hundredths and sums them — integer arithmetic only, because floating-point addition is order-dependent and the grade must not be.

contribution_i = round(score_i × weight_i × 100)
grade_hundredths = clamp(Σ contribution_i, 0, 10000)      // 8900 → 89.00

Missing evidence

on_unavailable decides what a metric that could not run costs:

PolicyEffectWhen to choose it
renormalizeThe absent metric's weight is redistributed across the metrics that did run, so missing evidence neither helps nor hurts.Default. The sandbox or the optional model is not the student's fault.
zeroThe weight stays where it is; absent evidence costs marks.When the metric is compulsory and its absence is a real failure.

Versioning on purpose

GRADER_VERSION and every analyzer version are hashed into the evaluation key. Changing a score formula therefore cannot silently re-grade old work: the key differs, so the old evaluation stays the answer to the old question, and a regrade is an explicit act that records lineage.

The reproducibility promise

evaluation_key = sha256( source_hash · rules_hash · testset_hash · toolchain_hash · grader_version )
report_hash    = sha256( canonical report JSON, minus non-deterministic text )

Same four inputs → same key → the stored evaluation is reused instead of re-run. Same output → same report_hash. That second hash is what scripts/verify-report.js recomputes on demand, with no sandbox call.

Why timing is evidence and not a score

Timing a program on a shared runner is noise: a constant-time program and an O(n) program can both finish in 1 ms, and the same program is slower on a busy host. The complexity metric therefore reads the AST, where the answer is deterministic, and records timings — when available — as corroboration the report shows side by side. A disagreement between the two is visible, not averaged away.

Rules that keep it honest

  • UUID primary keys — ids cannot be walked sequentially.
  • timestamptz everywhere — a mark has one meaning in every timezone.
  • JSONB only for genuinely open shapes — rule sets, evidence. Anything joined or filtered is a column.
  • Unique constraints carry meaning: one evaluation_key, one enrolment per student per course, one attempt number per student per assignment.
  • Nothing is deleted to re-grade: a new evaluation points at the old one through lineageOfId.

7. Reproducibility: keys, hashes, the golden corpus

This is the project's central claim, so it is the most heavily tested part.

What can legitimately change a grade

Only four things: the source bytes, the rule set, the test set, or the toolchain/grader version. Everything else — cache state, queue order, which worker ran it, how long it took — provably does not, because it is not in the key and not in the hash input. The report's Limitations block names the things that could not be measured, so “not measured” never reads as “zero”.

Why canonical JSON matters

Two rule sets that differ only in key order or whitespace must hash identically, or the cache and the audit trail would treat them as different rubrics. RFC 8785 (JSON Canonicalisation Scheme) sorts keys, fixes number formatting and forbids insignificant whitespace, giving one byte sequence per document.

8. The execution layer, the budget and the queue

The API never compiles C itself — Vercel has no toolchain and the assignment forbids Docker. One module is the only seam to the outside world.

Three providers behind one interface

ProviderCompiler flagsCPU / memory limitsStatus
onlinecompiler.io (default)NoNoOne synchronous call, free key, ~2 s round trip. Limits are recorded as requested, not enforced — the report says so.
Judge0 CEYesYesImplemented, switchable by env var. The provider to use when CPU/memory enforcement matters.
WandboxNo (fixed)NoKeyless last resort; results labelled differently because there is no timing data.

Each provider declares its capabilities; clampLimitsFor() records per-limit *_limit_enforced flags on the run, and the report's limitations block is generated from that record rather than from optimism.

Why a provider seam at all

The first choice (Judge0) needed a credit card for a keyed plan, so the default moved to onlinecompiler.io. Because the swap was one module and one env var, it cost no rewriting of the grading engine — which is the whole argument for the seam.

9. Security and permissions

Two roles and one institution, so the design favours things that can be read and audited over things that can be configured.

Session design

POST /auth/login — bcrypt compare, rate limited (5/min per IP + email)
▼
Access JWT (HS256, 15 min, httpOnly) + refresh token (256-bit random, 7 days, httpOnly, path /api/auth)
▼
Only SHA-256 of the refresh token is stored — a database leak does not hand over sessions
▼
Rotate on every refresh. Replaying a revoked token revokes every session for that user and clears cookies.

Checks applied to every request

CheckWhy
Origin check on mutationsCookie auth means CSRF is the real risk; a foreign Origin gets 403 CSRF_ORIGIN.
Role re-read from the databaseA role change applies on the next request; the token cannot carry a stale privilege.
Resource guard returns 404An instructor asking for someone else's roster learns nothing about whether that id exists.
Request-shape guardRejects __proto__/constructor keys and binary bodies before they reach a handler.
Upload guards.c only, ≤ 64 KB, no NUL byte, control-character ratio check.
Helmet headers, JSON body limitBaseline hardening with no per-route configuration to forget.
Secrets never in the repo.env ignored; .env.example is the contract; config.js validates with Zod and fails at boot if a required value is missing.

Why not a hosted auth service

Two roles, one course, one institution: a vendor would add a dependency, a callback URL per environment and a pricing cliff for about two hundred lines of code we can explain line by line. The accepted cost is documented: the in-memory rate limiter is per warm instance, so a cold start resets it and horizontal scaling multiplies the allowance.

A test that earned its keep

The load check was written to measure throughput. 11. Deployment and operations

Shape of the deployment

One Vercel project, two services (vercel.json): /api/* → Express, everything else → the Vite build
▼
Neon PostgreSQL — pooled connection string at runtime, direct string for migrations
▼
onlinecompiler.io — key in the environment, budget counted in the database

Why the two connection strings: serverless instances open a connection each and close it when frozen. Against a direct Postgres URL that exhausts max_connections during a class demo; the pooler fixes it. But pgbouncer in transaction mode cannot run migrations, so migrations take the direct URL. Getting this backwards produces “works locally, fails on first deploy”, which is why both are required at boot rather than defaulted.

First deployment, in order

  1. Add every variable from backend/.env.example to the Vercel project (backend service).
  2. Set APP_ORIGIN to the deployed origin and EXEC_SMOKE_ENABLED=false.
  3. Run npx prisma migrate deploy against the production direct URL.
  4. Open /api/health/ready — it should return ready: true. That single call is the proof a deployment works: database reachable, schema current, provider key accepted, budget remaining.
The failure that actually happens: “Requests from https://… are not allowed” on registration. That is the same-origin check doing its job, not a broken form — APP_ORIGIN is stale. docs/vercel.md covers it.

Background jobs

POST /api/internal/drain is guarded by X-Cron-Secret and answers 404 while the secret is empty (fail-closed: an unset secret must not mean an open endpoint). A cron entry calls it every minute with the secret; the drain grades one row at a time at the provider's rate. Without the secret, batch grading queues rows and nothing drains them — which the progress strip makes visible rather than silent.

Rollback

  • Redeploy the previous build in Vercel — no database rollback is needed for a code-only change.
  • Scoring changes bump grader_version, so old reports keep their hashes; a rollback does not re-grade history.
  • If a migration must be undone, restore from the Neon branch/snapshot rather than hand-writing a down-migration.

12. Decisions we made, and what we rejected

Six architecture decisions, each with the alternative that lost and the cost we accepted. The full text is docs/decisions.md.

DecisionRejected alternative and whyCost we accepted
Compile C on a remote provider behind a seamPiston: no compiler-flag field, so the syntax metric could not exist. Own VPS: a host, ops time and a security review we could not do in four weeks. Docker on Vercel: unsupported and excluded by the assignment.No SLA on the public provider; mitigated by a budget guard, polling and a fallback provider.
tree-sitter compiled to WASMRegex: cannot tell a loop inside a string from a loop, nor compute nesting. Native bindings: node-gyp and a C++ toolchain, fragile on Windows and unavailable on Vercel's build image.The grammar ABI must match the runtime; the working pairing is recorded so an upgrade is not a guess.
Postgres on Neon with split URLsA single direct URL: connection exhaustion under serverless. A proprietary backend: a rewrite if it ever moves.Two strings to configure correctly, enforced at boot.
Own JWT + rotating refresh cookiesClerk/Auth0/Supabase: a vendor and a callback URL per environment for ~200 lines. Bearer token in localStorage: an XSS bug hands over the session.The API must be same-origin in production (the rewrite provides it); the rate limiter is per instance.
Complexity from the AST, not timingsWall-clock curve fitting across three input sizes: noise on a shared runner, and a grade that changes when the host is busy.Static inference can be wrong (a hidden strlen in a loop). The report shows the inference and the measurement as corroboration.
LLM advisory, cached, weight 0Weighting model prose into the mark: provider-side model updates would change grades with no version bump we control.Less impressive-sounding feedback, in exchange for a mark that can be defended weeks later.

What measurement changed

  1. Judge0 collapses a null dereference and a division by zero to the same status (NZEC); the signal survives only in stderr, so it is exposed as a detail and no score depends on it.
  2. AddressSanitizer does work under the address-space limit (the plan predicted it would die), so sanitizer_run is a candidate metric with a fallback.
  3. The default provider had to change to one without a card requirement — and with that, the capability flags and the limitations block became necessary rather than nice to have.

13. Known limitations, stated honestly

LimitationConsequence
onlinecompiler.io enforces no CPU or memory limitsMetrics that depend on resource behaviour are weaker. Limits are recorded as requested, not enforced, and the report says so. Judge0 is the provider that can enforce them.
Cold provider cost is modelled, not measured8 calls per cold submission is a model derived from the analyzer list; measuring it needs more calls than the daily budget allows. The load check measures throughput (3 submissions, 41.1 s), not cost.
The login rate limiter is in-memoryPer warm instance: a cold start resets it and horizontal scaling multiplies the allowance. It blunts a script; it is not a distributed counter.
Similarity is a signal, not proofA flagged pair is a reason to look. The grade never changes automatically; a human decision is recorded.
Static complexity inference can be wrongA hidden O(n) call inside a loop reads as O(1). The report shows inference and measurement side by side so a reader can see the disagreement.
Cron is not configured in this repositoryThe drain route exists and is guarded; a scheduled caller must be added on the host. Until then, batch grading needs Grade all plus a drain call.
Public deployment needs the owner's accountsVercel and Neon credentials cannot be created from inside the repo, so the deployment is documented (docs/vercel.md) rather than claimed.
The demo video is not recordedThe shot list and timings exist in docs/report.md; recording is the owner's work.
Why this page exists. A grading system that hides its weak spots is worse than one that names them: a teacher can act on “the sandbox could not enforce a memory limit here”, but not on a silent zero.
