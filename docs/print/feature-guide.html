Before you start (5 minutes, once)

The app has two parts that run together: a server (it stores data and grades code) and a web app (what you click). You start both, then use the browser.

Step 1 — start the server

cd backend
npm start

Leave that window open. It prints that it is listening on http://localhost:3001. If it stops, everything else stops.

Step 2 — start the web app (second window)

cd frontend
npm run dev

It prints http://localhost:5173. That is the address you open in your browser.

Step 3 — sign in with a demo account

WhoEmailPassword
Instructor (teacher)prof@example.eduPassw0rd-Demo-2026
Studentstudent1@example.edu … student8@example.eduPassw0rd-Demo-2026

There is already a course called CS 101 - Programming in C. Its join code is ADDC2026.

Two windows, one browser. To show both roles at once, use one normal browser window for the instructor and one private/incognito window for the student. Otherwise the second login replaces the first.

Every feature below has the same three parts, so you can skim: What it does (plain words), Try it (numbered clicks), and Show it (a sentence to say out loud while you point at the screen).

Words you will see

WordWhat it actually means here
Submission / evaluationOne C file a student uploads, and the one grading run of it (queued, running, succeeded, partial or failed).
ReportThe result page: a grade out of 100, a table of marks per category, and the teacher's comments in machine form.
Rule setThe marking scheme: which categories count and how much each is worth. The weights must add to exactly 1.00.
AnalyzerOne checker inside the marking scheme, e.g. "does it produce the right output?" or "is the code readable?"
CohortAll the students in one course.
releasedThe teacher has allowed students to see their grade. Until then a student sees "submitted" only.
report_hashA short fingerprint of a report. Same input, same fingerprint — that is how we prove grading is repeatable.

One picture of the whole thing

Student writes C in the browser and presses “Submit and grade”
▼
The server saves the file and puts it in a queue (a waiting line)
▼
The queue hands it to the grading engine, one at a time
▼
The grading engine compiles and runs the code on a remote sandbox, then runs ~10 checkers
▼
A report is stored: grade out of 100, marks per checker, and a fingerprint
▼
Instructor reviews the cohort, releases grades, exports a spreadsheet
▼
Student reads the report, downloads it, or fixes the code and submits again

Nothing here needs a database administrator, a Docker container, or a compiler installed on your laptop. The code is compiled on a remote service the server talks to.

Part A — Getting in

1. The landing page

What it does: the public front door. It explains what the product is, shows the balance-scale logo, and gives two buttons: Sign in and Create account. If you are already signed in, the button becomes Open dashboard.

Try it
  1. Open http://localhost:5173.
  2. Read the headline, then click Sign in.
  3. Go back to the landing page while signed in and confirm the button now says Open dashboard.
Show it

“This is the public page — nothing here needs a login. Notice the button changes once I am signed in, so I never have to hunt for the way back.”

2. Create an account (two kinds)

What it does: makes a new user. You choose Student (“join courses, submit code”) or Instructor (“create courses, grade work”). Becoming an instructor requires a secret signup code, so a student cannot promote themselves.

Try it
  1. Click Create account.
  2. Pick Student, fill name, email and a password (at least 8 characters), then press Create account.
  3. You land in the student dashboard, already signed in.
  4. Now try the same form with Instructor selected and no signup code: the form refuses and tells you a code is required. That refusal is the feature working.
Show it

“Anyone can join as a student. Becoming a teacher needs a code the institution holds — so roles are not self-service.”

3. Sign in, and stay signed in safely

What it does: logs you in and keeps you logged in while you work. The browser holds two cookies: a short one (15 minutes) that proves who you are, and a long one (7 days) that quietly renews it. Neither is readable by page scripts, so a bug in the page cannot steal your session. If someone tries to reuse an old renewal cookie, every session for that account is cancelled.

Try it
  1. Sign in as prof@example.edu.
  2. Reload the page a few times — you stay signed in.
  3. Wrong password once: you get a clear error, not a blank page.
  4. Press Log out; you are sent back to the public pages and the dashboard no longer opens.
Show it

“The session survives a refresh but not a logout, and the browser never exposes the token to the page.”

4. Light, dark, or follow the system

What it does: switches the colour theme. Your choice is remembered and applied before the page draws, so there is no white flash when you reload.

Try it
  1. Find the theme button in the top bar and click it through its options.
  2. Hard-reload the page (Ctrl+F5). The theme stays, with no flash.
  3. Close the browser and open it again: still your choice.
Show it

“Watch the reload — no white flash. That is a deliberate three-line script that sets the theme before the first paint.”

Part B — The student journey

5. Join a course with a code

What it does: puts you in a class. Codes are 8 characters and not case-sensitive, and joining twice is harmless — you stay in the course once.

Try it
  1. Signed in as a student, look at the Join a course card on the dashboard.
  2. Type addc2026 in lowercase and press Join course.
  3. The course appears in your list immediately, with its assignments.
  4. Press Join course again with the same code: you are already in it, nothing breaks.
  5. Try a wrong code: you get a friendly “code not found”, not an error stack.
Show it

“The instructor reads one code out loud, everyone types it, and the class appears. No email invitations, no spreadsheets.”

6. Open an assignment and write code in the browser

What it does: shows the assignment instructions, the due date, your previous attempts, and a code editor with C syntax highlighting. You can type or upload a .c file; the app tells you straight away if the file is the wrong type or too large (over 64 KB).

Try it
  1. Open the CS 101 course, then the assignment.
  2. Paste this program into the editor:
#include <stdio.h>

int add(int a, int b) {
    return a + b;
}

int main(void) {
    int a, b;
    if (scanf("%d %d", &a, &b) != 2) {
        return 0;
    }
    printf("%d\n", add(a, b));
    return 0;
}
  1. Try uploading a .txt file: it refuses and explains that only .c is accepted.
Show it

“The student never leaves the page — editor, checks and submission are one screen.”

7. Submit and watch it grade

What it does: sends the file for marking. The page does not freeze: it shows the stage (“compiling…”, “running tests…”), then the result. The button stays disabled while a run is in flight so a double click cannot submit twice.

Try it
  1. With the program above, press Submit and grade.
  2. Watch the button text change through the stages. This takes a few seconds because the code is compiled on a remote service.
  3. When it finishes you get a confirmation and a link to the report.
If it says “Submitted. Your grade appears once your instructor releases it”, that is correct behaviour, not a bug: grades stay hidden until the teacher releases them.
Show it

“Notice the stages: the page is telling me exactly what the server is doing, instead of a spinner that could mean anything.”

8. Read the report

What it does: explains the grade. You get the mark out of 100 with a plain verdict (Good, Needs work, Review required), a table with one row per marking category showing the score, the weight, and the marks it contributed, plus the evidence behind each row, a side-by-side difference against a reference solution where the assignment has one, a Limitations box saying what could not be measured for this run, and the fingerprint (report_hash).

Try it
  1. Open the report from the submission confirmation.
  2. Find the big grade and the verdict text.
  3. Scroll to the metric table: every category shows score → weight → marks. Check that the marks add up to the grade.
  4. Read the limitations box: it lists what this sandbox could not enforce.
  5. Copy the report_hash — a 64-character fingerprint.
Show it

“This is not a black box: each mark shows its weight and its share, and if something could not be measured the report says so instead of quietly giving zero.”

9. Download or print the report

What it does: gives you the same report as a JSON file (for a script or a spreadsheet) or a plain-text file (for a portfolio or an email), and a print layout that turns the page into a clean PDF.

Try it
  1. On the report page press the download button and choose JSON — the file opens in any editor.
  2. Download the text version and open it in Notepad: it is readable without any tool.
  3. Press Print and look at the preview: navigation and buttons disappear, only the report prints.
Show it

“JSON for machines, text for humans, print for an archive — from one stored report.”

10. Submit again, and see your attempts

What it does: every upload is kept as its own attempt, numbered. Re-submitting the same file still produces a report of its own, but the expensive part — compiling and running the code — is reused from a cache, so it costs nothing and grades identically.

Try it
  1. Submit the same program a second time.
  2. Open both reports: the grade and the report_hash are identical.
  3. Change one number in the program, submit again: the grade changes and the attempts list shows attempt 3.
Show it

“Same file twice gives the same fingerprint and costs nothing extra — that is the promise of the whole project, visible on one screen.”

Part C — The instructor journey

11. Create a course and share one code

What it does: makes a new class and generates its 8-character join code. The course page lists the students who joined, with their activity, and lets you remove someone from the roster.

Try it
  1. Signed in as prof@example.edu, open the instructor dashboard.
  2. Fill in “create a course” (title and code, e.g. CS 102 — Data Structures).
  3. The new card shows its join code; click it to copy.
  4. Open the course and look at the roster: names, emails, how many submissions each student has.
Show it

“One code per course, one roster that updates itself as students join.”

12. Create an assignment and its hidden test cases

What it does: defines the work: title, description, due date, whether late work is allowed, and the tests used for marking. Each test is an input and the expected output. Students never see them. Bulk paste lets you add many tests at once instead of one form at a time.

Try it
  1. Open a course and create an assignment (title: Add two integers).
  2. Open its Tests tab and add one test: input 2 3, expected output 5.
  3. Use Bulk paste to add two more: -4 4 → 0 and 1000000 2000000 → 3000000.
  4. Delete one test and watch the list shrink.
Show it

“Tests are data, not code: the instructor types the inputs and the expected output, and the engine does the rest.”

13. The rule set editor — the marking scheme

What it does: lets you decide what counts. Each row is one category with a weight; a live total shows how much of the grade is allocated and publishing is blocked until the weights add to exactly 1.00. Before publishing, it shows a diff against the current version, so you can see what is about to change for every future mark.

Try it
  1. Open the assignment's Rule set tab.
  2. Find the weight total. Change one weight so the total is no longer 1.00.
  3. Press publish: it refuses and explains why. (That refusal is the feature.)
  4. Put the weight back, press publish again: it succeeds and the version number goes up.
  5. Look at the publish diff: it names the fields that changed.
Show it

“A rubric where the weights do not add up is a rubric that cannot produce a mark, so the editor simply will not let it through.”

14. Publish the assignment

What it does: opens the assignment to students. It refuses to publish unless the assignment has tests, a published rule set, and (for the smarter checkers) a reference solution — so an empty assignment cannot go live by accident.

Try it
  1. On an assignment with no tests, press Publish assignment: it refuses, naming what is missing.
  2. Add tests and a rule set, then publish again: the status becomes published and students can submit.
Show it

“The system refuses to publish an assignment a student could submit to and get nonsense back.”

15. The cohort table — every student, one screen

What it does: lists submissions with student, attempt, time, and grade. You can filter and page through them, export everything to CSV for a spreadsheet, and per row either Release the grade to the student or Regrade it. A regrade creates a new evaluation that remembers which one it came from, so history is never overwritten.

Try it
  1. Open the assignment's Cohort tab.
  2. Filter by a student's name and confirm the list narrows.
  3. Press the export button: a CSV downloads. Open it and check the columns.
  4. On a row, press Release: the student can now see the grade. Press again (Unrelease) to hide it.
  5. Press Regrade on one row and watch the new evaluation appear with the same grade.
Show it

“Release when marking is done, export for the registry, regrade when a rubric changes — and the old marks stay in the history.”

16. Grade all — batch grading with a visible queue

What it does: queues every submission that has not been graded yet and shows a progress strip: done of total (percent) · queued · running · failed. It updates by itself every few seconds. Work is done one at a time, at the speed the remote compiler allows, so it cannot be rate-limited into failure.

Try it
  1. In the Cohort tab find the queue strip and note the counts.
  2. Press Grade all.
  3. Watch the numbers change without touching the page: queued falls, running shows 1, done rises.
  4. When it reaches 100%, open a report to confirm a real grade was produced.
Show it

“One click for a whole class, and the counter tells me exactly how far along it is — no refreshing, no guessing.”

17. Similarity — flagging lookalike code

What it does: compares every submission in the assignment with every other one and lists the pairs that look alike. A flag is a reason to look, never an automatic punishment: you decide acknowledge or flag, and your decision is stored with a note.

Try it
  1. Open the Similarity tab and press the scan button.
  2. When it finishes, the list shows pairs with a similarity score.
  3. Pick one pair and record a decision with a short note.
  4. Reload: the decision is still there.
Show it

“This is an originality signal, not a verdict — the grade never changes automatically; a human decision does.”

18. The activity feed

What it does: a chronological list of what happened on the assignment: rule sets published, grades released, regrades run, similarity decisions made. It answers “who changed the marking, and when?”

Try it
  1. Publish a rule set and release one grade.
  2. Open the Activity panel: both actions are listed with a timestamp.
Show it

“Every decision that affects a mark leaves a trace, so a disputed grade has a history rather than a shrug.”

Part D — Trust and everyday operations

19. Same code, same grade — proven, not claimed

What it does: the same file, marked under the same rule set, always produces the same grade and the same report_hash. A command-line checker can re-check a stored report and tell you whether it still recomputes. A larger “golden corpus” run marks 18 sample programs under 3 marking schemes, 5 times each, and confirms all 270 results are identical.

Try it
  1. Submit one file twice; compare the two report_hash values (identical).
  2. In a terminal: cd backend then node scripts/verify-report.js <evaluation-id>. It prints PASS and says the report recomputes to the stored hash.
  3. For the full proof: npm run golden. It takes several minutes and prints the 270-run table into docs/samples/golden-corpus.csv.
Show it

“Anyone can check a stored grade without asking the sandbox again — that is what makes the mark defensible two weeks later.”

20. Health pages — “is the system okay?”

What it does: two plain addresses. One says the server is alive and can reach the database. The other is the honest one: it checks database, database version, the compiler service key and the remaining daily budget, and lists each as ok or failing.

Try it
  1. Open http://localhost:3001/api/health — you should see "db": "ok".
  2. Open http://localhost:3001/api/health/ready — every check should say ok and the top line ready: true.
  3. If grading ever fails, this is the first page to open: it names the broken piece.
Show it

“One URL answers ‘why might a submission fail right now?’ before a student has to report it.”

21. Roles and privacy

What it does: keeps students and instructors apart. A student who types an instructor address gets a page saying that area is for instructors. Asking for someone else's course or roster returns “not found” rather than “forbidden”, so nobody can probe which ids exist.

Try it
  1. Signed in as a student, go to http://localhost:5173/instructor — you see “This area is for instructors”.
  2. Signed in as an instructor, try to open a course you do not own: not found.
  3. Signed out, open /student: you are sent to sign in.
Show it

“Permissions are checked on the server for every request, and the answer never leaks whether someone else's data exists.”

22. Works on a phone, and with a screen reader

What it does: the layout reflows down to a 360-pixel-wide screen, keyboard focus is visible, form fields have real labels, and an automated accessibility check reports no critical problems on the sign-in page and the dashboard.

Try it
  1. Make the browser window very narrow — the tables become cards and nothing scrolls sideways.
  2. Press Tab repeatedly: every control shows where the focus is.
  3. Automatic proof: cd e2e then npx playwright test (both servers must be running). All 8 checks pass.
Show it

“The same app on a phone in class, and it passes an automated accessibility check rather than just looking fine.”

Before you present — 6-point check

  • Backend and frontend both running; the readiness page says ready: true.
  • EXEC_DAILY_BUDGET has room left (the readiness page shows the count).
  • One student account already joined the course, so the cohort is not empty.
  • The assignment already has tests and a published rule set.
  • A private window is signed in as a student, ready, before you start talking.
  • The report page is pre-loaded in a background tab in case the sandbox is slow.

If something goes wrong while you present

SymptomWhat to do
Submit button spins for a long timeThe remote compiler is slow. Say so: grading is a queue, and the report will still be correct. Do not click twice.
“Grade appears once released”Correct behaviour. Press Release in the cohort table, then reload the student's report.
Readiness page shows the budget exhaustedThe daily sandbox allowance is spent. Wait for 00:00 UTC, or raise EXEC_DAILY_BUDGET in backend/.env and restart.
Server stoppedRestart npm start in backend; nothing is lost, all data is in the database.
A grade looks wrongOpen the report: the metric table shows which checker gave what. That is the answer, not a guess.
